# Test 1 — the W-sweep (data-dependency width) microbenchmark for Q1

Branch: `exp/dd-test1` (based on `numa-alloc`; `numa-alloc` is not modified or merged).

## Question

The runtime gap between the *compiled* engine (Typer, `q1_hyper`) and the
*vectorized* engine (Tectorwise, `q1_vectorwise`) on the cache-resident Q1 is
hypothesized to be driven by instruction count. Tectorwise materializes every
intermediate to memory (a load/store per intermediate per tuple); Typer keeps
intermediates in registers. To make this measurable we inject *W* extra
per-tuple intermediate values into the same Q1 scan and observe how the two
engines' costs grow with the data-dependency width *W*.

## The kernel

`include/benchmarks/tpch/DdKernel.hpp` defines `dd::DdKernel<W>::run(ep, disc)`.
It produces **W distinct scalar `int64_t` SSA locals**, each data-dependent on
the per-tuple inputs:

```
local_k = ep * C_k + (ep ^ (disc + k))          (k = 0 .. W-1)
```

with distinct constants `C_k = ddConstant(k)`. The W locals are generated by
**recursive template / integer-sequence unrolling** (no `std::array`, no runtime
loop whose bound is W):

```cpp
template <int... ks>
static int64_t sumAll(int64_t ep, int64_t disc, std::integer_sequence<int, ks...>) {
   return (gen<ks>(ep, disc) + ...);   // straight-line fold; nothing is dead
}
```

All W locals feed the reduction, so none can be dead-code eliminated, and every
`C_k` differs so no two locals can be CSE'd or constant-folded together. W is a
**compile-time** constant on the Typer side, so the machine code is straight-line
register pressure (verified in the asm gate below).

## Typer variant — compile-time W

`src/benchmarks/tpch/queries/q1_dd.cpp`:

- `template<int W> q1_dd_hyper_impl<W>` — a byte-for-byte mirror of base
  `q1_hyper` (same scan, `l_shipdate` filter, 4-group group-by, same four
  aggregates), with `NOVECTORIZE` (the same attribute used by base `q1_hyper`).
  The kernel result is accumulated into a dedicated `localSink` per morsel, then
  `sink.fetch_add(...)` into a separate `std::atomic<int64_t> sink`, which is
  `escape()`d — entirely separate from the real Q1 aggregates, so Q1's reported
  answer is unchanged at every W.
- `q1_dd_hyper(db, nrThreads, W)` — runtime dispatcher mapping a runtime W to
  the compile-time instantiation via `DD_WIDTHS = {2,4,6,...,32}` (explicit
  switch). An unsupported W is a **hard error** (`exit(1)`, no silent fallback).

## Tectorwise variant — runtime W

`Q1Builder::getQueryDd(int W)` extends the base `q1_vectorwise` projection chain
with **W intermediate buffers** (`dd_buf_base + 0 .. +W-1`), one expression per
intermediate (`buf[k] = buf[k-1]*C_k + extendedprice`), plus a final expression
that sums all W into the dedicated `dd_sink` buffer. The real Q1 aggregates and
result columns are unchanged; the sink is emitted as an extra `dd_sink` result
column so the harness `escape` keeps it live. `q1_dd_vectorwise(...)` wraps this
in the same `WorkerGroup`/`SharedStateManager` pattern as base.

Buffer ids use a high numeric base (`dd_buf_base = 64`) to avoid colliding with
the existing Q1Builder enum ids. Because the vectorwise builder stores buffers in
an `unordered_map` keyed by int id (no fixed buffer-count cap), no engine-side
buffer-cap change was needed to support W up to 32.

## Harness

`src/benchmarks/tpch/run.cpp` adds a `-w <W>` option (default `0` = disabled):

- `-q 1 -e h -w 16` runs `q1_dd_hyper` labelled `q1dd h W16 <tN>` (W printed
  ahead of the ` tN` thread token).
- `-q 1 -e v -w 16` runs `q1_dd_vectorwise` labelled `q1dd v W16 <tN>`.
- The `Config:` line prints `W: <W>`.
- One W per invocation (a sweep is one invocation per W).

## Structural asm gate

`scripts/dd_verify_asm.sh [binary]` analyzes the per-tuple scan loop of
`q1_dd_hyper_impl<W>`. The per-tuple compute is inlined into the TBB morsel lambda
(`q1_dd_hyper_impl<W>(...)::{lambda(blocked_range<unsigned long> const&)#2}::operator()`),
NOT the NOVECTORIZE impl function. Within that lambda the inner per-tuple loop is
located by a structural signature: its loop-closer (backward jump) is immediately
preceded by the tuple bound-check `cmp` and its span contains the DdKernel
(`movabs $Ck`). The bounded hash-probe sub-loop also ends in `cmp`+`jne` but
contains no `movabs`, so the signature picks the tuple loop uniquely (verified:
W=2 loop = `0x116f1c..0x117072`, W=18 loop = `0x119adc..0x119ddb`). Per W it prints
the symbol analyzed, the loop start/end addresses, the loop instruction count, and
(`--dump <W>` prints the full disassembly of the identified loop):

| W  | per-tuple loop         | inst | arith (scalar/vec) | spills store/reload | regs GP/vec | loop closers |
|----|------------------------|-----:|-------------------:|--------------------:|------------:|-------------:|
| 2  | 0x116f1c..0x117072    |  90  | 24 (24/0)          | 3 / 0               | 92 / 0      | 5            |
| 8  | 0x117dfc..0x117ff5    | 126  | 47 (47/0)          | 3 / 0               | 131 / 0     | 5            |
| 16 | 0x1194ac..0x119775    | 173  | 79 (79/0)          | 3 / 0               | 185 / 0     | 5            |
| 18 | 0x119adc..0x119ddb    | 185  | 87 (87/0)          | 3 / 0               | 197 / 0     | 5            |

The **primary gate**:

1. **arith ops rise monotonically with W** (24 → 47 → 79 → 87): the straight-line
   SSA-local unrolling adds real per-tuple work (no DCE collapse). **PASS**.
2. **no W-trip loop over the intermediates**: loop-closer count stays constant
   (5 = 5 = 5 = 5) while arith ops grow, so the extra work is unrolled, not wrapped
   in a loop whose trip count is W. **PASS**.

The disassembly confirms the kernel is straight-line scalar **GP-register** code:
W=18 shows exactly 18 `movabs $Ck; imul %rdx,%rdi; lea k(%rcx),%rsi; xor; add`
steps, all in `%rax/%rbx/%rcx/%rdx/%rsi/%rdi/%r8-%r15`. No vector operands at any W
(vec = 0), so the allocator is NOT using x86-64/AVX-512 vector registers for the
scalars (the double-register-budget hypothesis does not apply here).

### Spill finding (measurement-corrected)

The earlier flat spill=0 was a **matcher bug**, not a real zero: the spill matcher
only looked for `%rsp`-based stack operands, but `-fno-omit-frame-pointer` keeps
`%rbp` as the frame base, so every stack slot (`disp(%rbp)`) was missed. The
corrected matcher counts ANY opcode with a stack-frame operand (both `%rbp`/`%rsp`,
both directions) and prints each match verbatim.

With the loop correctly identified and the matcher broadened, the result is:
**3 fixed stores and 0 reloads, constant across all W**. The three stores are the
group-key construction bytes in every per-tuple iteration
(`mov %[sr]i?l,-0x41(%rbp)` returnflag, `mov %r10b,-0x42(%rbp)` linestatus,
`mov %rdx,-0x40(%rbp)` hash) — fixed overhead, not kernel spills. The W
intermediates themselves never spill in this build: **the kernel lives entirely in
GP registers up to W=18 with zero W-scaling spill/reload**. This is a genuine
finding in the correctly-identified GP inner loop (see the W=18 `--dump`), not a
failure.

## Correctness

`q1_dd_hyper_impl<W>` shares the identical scan/filter/group-by/aggregate code
with base `q1_hyper`; the synthetic work is routed to a separate escaped sink.
The real Q1 result (4 groups × `sum_qty, sum_base_price, sum_disc_price,
sum_charge, count_order`) was verified identical across base `q1 h`, `q1dd h W2`,
and `q1dd h W32`, and across base `q1 v` and `q1dd v W32` (sf1 data). The dd
variants do not perturb the real Q1 answer at any W.
