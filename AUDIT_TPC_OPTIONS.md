# Audit: VectorWise build options, over-tuning and TPC-H compliance

Date: 2026-10-04. Branch `query1`, HEAD `2b1cbdf` plus the uncommitted working tree (`VW_JOIN_DISPATCH`, `VW_JOIN_SEMI_MAX_BYTES`, `VW_GROUP_HAVING`). Follows `VW_OPTIONS.md` (2026-10-03, HEAD `6198f40`). That document describes what each option does; this one only judges the options.

Scope:
- options added or changed since `6198f40`: `git log 6198f40..HEAD` (b8f1b4a run heads, ec81f62/490eb4b/f484214 dense projections) and the uncommitted diff (`CMakeLists.txt`, `Operators.{hpp,cpp}`, `QueryBuilder.{hpp,cpp}`, `Operations.{hpp,cpp}`, `q18.cpp`);
- the plan markers `HashJoinBuilder::semi()` on Q3/Q5/Q9/Q18;
- a short re-check of the older options in `VW_OPTIONS.md`.

Line numbers refer to the working tree as of this audit.

## TL;DR

- **Context.** Every query plan in this repo is hand-built, in `src/benchmarks/tpch/queries/*.cpp`, with fixed substitution parameters (`include/benchmarks/tpch/Queries.hpp:32`, `:234`). Under TPC rules that is already a benchmark-special implementation: there is no SQL front end and no optimizer. Each option below is judged against that baseline. The question is whether it adds query-, data- or machine-specific knowledge beyond what a hand-written plan already contains.
- **TPC-invalid as is (3):**
  - **`semi()` markers on Q3, Q5 and Q9.** They rewrite inner joins into semi joins on the claim that the build keys are unique. Nothing checks that claim, and nothing derives it from a declared constraint: the schema declares no keys at all (`Database.hpp:50-59`, `Import.cpp:249-366`). The Q18 marker is fine, because there uniqueness follows from the plan's own GROUP BY.
  - **`VW_PROJ_DENSE`.** It is opted into only by Q1's plan (`q1.cpp:386-411`, `:459-472`). It pays off only because Q1's date predicate keeps about 95–98% of rows. That is knowledge of the data and of the parameter range, used to pick a plan.
  - **`VW_Q9_FIELD_ORDER`.** Query-specific code: a macro that reorders one join's payload in Q9 only (`q9.cpp:292-308`). It is harmless because no recommended configuration enables it.
- **Over-tuned to one machine (1):**
  - **`VW_JOIN_SEMI_MAX_BYTES`** (8 MiB). It is the crossover point from one Zen 4 microbenchmark sweep (`JOIN_DISPATCH_STUDY.md:23-25,164`). At SF1 it changes no TPC-H decision, so it is not fitted to a query, but it is a constant taken from one machine.
- **Note (thresholds with reasonable motivation that should become hardware facts):**
  - `VW_JOIN_BLOOM_MIN_KEYS` and `VW_JOIN_TWOPHASE_MIN_SLOTS` (both 4096, both justified in comments by Q18's 57-key build);
  - the Bloom filter's adaptive skip (more than 50% of probes pass, then skip 31 vectors);
  - the 2^27-bit semi bitmap cap;
  - `VW_JOIN_DISPATCH`'s `buildKeysSelected` proxy;
  - `VW_GROUP_RUN_HEADS`. It is correct for any row order, but its speedup comes from lineitem's `l_orderkey` load order.
- **OK:** `VW_GROUP_HAVING` (a general HAVING operator; Q18's use is an exact rewrite), `VW_JOIN_FUSED_PROBE`, `VW_PROJ_DENSE_WIDTH`, and the older options.
- **Found outside the VW scope, missed by the previous audit:** `HYPER_Q1_DIRECT_AGG` hard-codes the `l_returnflag` domain `{A,N,R}` and maps any other value to `R` (`q1.cpp:112-121`). That is TPC-invalid, and incorrect on other data. `HYPER_Q1_SIMD` requires it.

## Spec basis (from general knowledge, not checked against the text)

No TPC-H specification is available in the repo or on this machine. Everything below comes from my general knowledge of TPC-H (v2/v3), not from the text. Clause numbers are given only where I am reasonably confident, and are marked `(?)` otherwise.

- **General implementation guidelines (Clause 0.2, I believe).** Benchmark-special implementations are prohibited. An optimization has to be generally applicable, not built mainly to speed up the benchmark. The guidelines list as examples code that recognizes a specific benchmark query, and use of knowledge about the benchmark data or parameters that a general product would not have.
- **Query compliance (Clause 2.x (?)).** Queries are run from their SQL text, with minor approved variants. Substitution parameters are generated by qgen per run, so a plan has to be correct, and fairly costed, for the whole parameter range rather than one validation value. Rewrites are allowed only when they are semantically equivalent in general, which includes for data the declared constraints allow.
- **Constraints (Clause 1.4.x (?)).** Primary and foreign keys are listed in the schema definition, and an implementation may declare them. Using them, for example inferring uniqueness from a declared primary key, is legitimate when the engine actually has them declared, and enforces them where the spec requires that. Using uniqueness that is not declared means relying on an undeclared data property.
- **Physical layout and partitioning (Clause 1.5.x (?)).** Some clustering and partitioning is permitted, by key or date columns. I do not remember the exact limits. Relying on dbgen's output order (lineitem in `l_orderkey` order) for *correctness* would be non-compliant. Being merely faster under that order is generally accepted.

Because of the context above (hand-built plans, fixed parameters), no build of this repo can be TPC-H compliant as a whole. The verdict "TPC-invalid as is" below means that the option adds a violation of its own, on top of the hand-planning baseline, that a general engine would not have.

## Per-option findings

### `HashJoinBuilder::semi()` markers (Q3, Q5, Q9, Q18)

**Evidence.**
- Definition: `QueryBuilder.cpp:525-528`. It only sets `join->semiJoin = true`.
- The contract is documented at `QueryBuilder.hpp:84-96`: "ASSUMPTION: the build keys are unique; nothing checks it."
- Markers:
  - `q3.cpp:193` (customer → orders, on `c_custkey`);
  - `q5.cpp:221` (region → nation, on `r_regionkey`);
  - `q9.cpp:259` (part → partsupp, on `p_partkey`);
  - `q18.cpp:254` (group-by output → orders).
- The schema carries no constraints. `Relation` is attributes, name and tuple count only (`Database.hpp:50-59`), and the importer declares column names and types only (`Import.cpp:249-366`). The repo has no notion of a primary key.

**What the marker changes.** On Q3/Q5/Q9 the SQL is an inner join. The rewrite to a semi join is equivalent only if each probe row matches at most one build row, that is, if the build key is unique.
- If a build key were duplicated, the bitmap path would *drop* rows the inner join repeats. This is described in `VW_OPTIONS.md` §3, and in `QueryBuilder.hpp:90-95`.

**Over-tuning.** None. The rewrite is the textbook one: an inner join to a PK side that contributes no columns is a semi join. Hyper's plans in this repo make the same rewrite (`q3.cpp:74,104`, `Hashset::contains`), so the comparison between the engines is symmetric.

**TPC verdict.**
- **Q18: OK.** The build side is the output of `GROUP BY l_orderkey` (`q18.cpp:219-254`), so uniqueness follows from the plan itself, and `IN (subquery)` *is* a semi join in the SQL.
- **Q3, Q5, Q9: TPC-invalid as is (strict reading).** The facts relied on, `c_custkey`, `r_regionkey` and `p_partkey` being primary keys, are constraints that TPC-H lets an implementation declare. Here they are neither declared nor derived nor verified. They are asserted by a hand-written annotation. A general engine applies this rewrite only when it can prove uniqueness from declared constraints or from the plan. *Practical risk is low: the TPC-H data satisfies these keys, and the hand-built plan already encodes far more knowledge than this.*

**Fix, either of:**
1. Add key metadata to `Relation` (for example `primaryKey` columns set in `Import.cpp` from the TPC-H schema). Then have `semi()` (or an automatic rule in `HashJoinBuilder`) verify that the build key column is the declared key of its base relation and that no build values are gathered, and throw otherwise.
2. A cheap run-time guard: in `semiSetBits`, test before setting each bit. A duplicate key means uniqueness fails, so turn `semiOn` off and run the join as an inner join. The hash path would still need the same guard for the Q18 direction (a semi join run as an inner join); the GROUP BY guarantees uniqueness there anyway.

Option 1 matches the spec's model (declared constraints). Option 2 makes the marker safe on any data.

### `VW_JOIN_SEMI`: bitmap semi join

**Evidence.**
- CMake: `CMakeLists.txt:479-489`.
- Candidate test: `Operators.hpp:298-302` (`semiCandidate`: marker, one int32 key per side, no build values). These are plan facts.
- Key range: `semiRange()` (`Operators.cpp:884`), computed from the actual build.
- Cap: `hi - lo < 2^27` (`Operators.cpp:1653`, non-dispatch build).

**Over-tuning.**
- The decision uses plan facts and a run-time build summary (min and max key). That is the general array-join / perfect-hash technique, and it adapts to whatever data arrives.
- The 2^27-bit (16 MiB) cap is a memory bound, not fitted to TPC-H. At SF1 the marked joins need about 19 KiB (Q3, 150K custkeys), a few bytes (Q5), about 25 KiB (Q9, 200K partkeys) and about 703 KiB (Q18, which uses the `o_orderkey` range). All are far below the cap.
- Verdict: **OK**, with one note. Key *density* is assumed favourable only implicitly: a sparse range wastes memory up to the cap. That is a cost issue, not a correctness or compliance issue.

**TPC verdict:** OK as a mechanism. It inherits the Q3/Q5/Q9 marker issue above, because the bitmap path is the one that drops duplicate matches.

### `VW_JOIN_SEMI_MAX_BYTES` (uncommitted)

**Evidence.**
- `CMakeLists.txt:505` (default 8388608) and its use at `Operators.cpp:1651`.
- Source of the value: `JOIN_DISPATCH_STUDY.md:23-25,152-164`. On Zen 4 the bitmap is 2–4× faster up to 8 MiB and 2× slower at 16 MiB. "The crossover moves with the cache sizes, so this default is to be checked per machine" (`:164`, `:112`).

**Over-tuning: over-tuned (machine).** The constant is the crossover from one machine's microbenchmark. It is not fitted to a query: at SF1 every marked join's bitmap is at most about 0.7 MiB, so any cap above 1 MiB gives identical TPC-H decisions. It would start to matter around SF ≥ 12 for Q18, whose `o_orderkey` range grows with SF. That is the scaling regime where a machine-fitted number becomes a hidden scale-factor knob.

**TPC verdict:** note. Hardware-dependent tuning parameters are normal for any product, provided they describe the hardware rather than the benchmark.

**Fix.** Express it as a fraction of a cache level read at start-up (`sysconf(_SC_LEVEL2_CACHE_SIZE)` / `_SC_LEVEL3_CACHE_SIZE`, or `/sys/devices/system/cpu/cpu0/cache`). Alternatively, keep the build option but record the per-machine value with its sweep (the `join_dispatch` config already produces `joindispatchbench.csv` per machine).

### `VW_JOIN_DISPATCH` (uncommitted)

**Evidence.**
- CMake: `CMakeLists.txt:491-519`.
- `resolvePaths()`: `Operators.cpp:1536-1576`, called once per operator at `:1673`.
- Bloom gate: `wantBloom = buildKeysSelected` (`:1613`). It is set by `addBuildKey(col, sel, ...)` (`QueryBuilder.cpp:327-329`).
- The filter is not allocated for semi candidates (`Operators.cpp:1621`), and is allocated late when the bitmap is ruled out (`:1658-1662`).

**Over-tuning.**
- The structure is good. It removes the per-vector adaptive switch and decides from plan facts plus a build summary. This is the "decision from general plan facts" category.
- Two inherited constants: `VW_JOIN_BLOOM_MIN_KEYS` and `VW_JOIN_SEMI_MAX_BYTES` (see their sections).
- The proxy "build keys read through a selection means probes may miss" (`JOIN_DISPATCH_STUDY.md:110,310`) is a *plan* fact, so it is general. It reflects what is typical of FK→PK joins with a filtered PK side, not any one query. Its known misfire is Q9 J3 (a filter it does not need, about 43K × ~1 ns), and the study documents it.
- In a hand-built plan, whether the author wrote the `sel` overload is itself a hand decision. In a real optimizer it would follow from "a filter under the build side", which is equivalent.

**TPC verdict:** **OK**. Note: the per-vector adaptive version it replaces was also acceptable. This one is more deterministic.

**Fix (optional).** Replace the proxy with an explicit builder annotation, or with an estimate of the build side's selectivity relative to the base table (`found / nrTuples`, both known after the build). The second is a run-time summary and needs no new plan facts.

### `VW_JOIN_BLOOM`, `VW_JOIN_BLOOM_MIN_KEYS`, adaptive skip

**Evidence.**
- CMake: `CMakeLists.txt:438-458` (16 bits per key, MIN_KEYS 4096).
- Comment justifying MIN_KEYS: "covers Q18's 57-key joins" (`VW_OPTIONS.md` §3; `Operators.hpp:201`).
- Adaptive skip: `if (m * 2 > n) bloomSkip = 31;` (`Operators.cpp:1053`, `:1168`). Rationale in a comment: "mostly-hitting joins, e.g. Q9's" (`:982-984`).

**Over-tuning: note.**
- MIN_KEYS = 4096 was motivated by Q18, but the TPC-H build sizes at SF1 are either tiny (1 region, 5 nations, 57 orders) or at least about 10K. Any value from about 60 to about 10K gives the same decisions, so 4096 is not fitted to a measured edge. Conceptually it is "the build's directory is L1/L2-resident, so a filter cannot save a miss": a hardware fact stated as a key count.
- The 50% pass rate and the 31-vector skip are an untuned cost-model guess. They react to observed run-time data, which is the normal adaptive-execution design (Vectorwise, Umbra and others do similar), and are not tied to a query's measured hit rate. The study shows the always-on filter loses at 90–100% hits (`JOIN_DISPATCH_STUDY.md:27,182`), so 50% is conservative rather than fitted.

**TPC verdict:** OK.

**Fix.** Derive MIN_KEYS from cache size (directory bytes = slots × 8 compared with L1d or L2). Leave the skip constants, or document them as a cost-model parameter.

### `VW_JOIN_FUSED_PROBE`

**Evidence:** `CMakeLists.txt:460-477`. It applies when the probe side has a single int32 key hashed by `hash_(sel_)int32_t_col` (`VW_OPTIONS.md` §3). Hashes are bit-identical to the plan's primitive.

**Verdict:** **OK / OK.** It keys on a plan fact (key arity and type) and applies to every such join.

### `VW_GROUP_HAVING` (uncommitted)

**Evidence.**
- CMake: `CMakeLists.txt:521-530`.
- Builder: `QueryBuilder::HashGroupBuilder::having` (`QueryBuilder.cpp:613-646`). It takes any output column of the group-by and any selection `Expression`, and rejects misuse (`:617-627`).
- Operator: `HashGroup::next` (`Operators.cpp:1888-1911`). Output gather through the selection: `GatherOpValSel` (`Operations.cpp:59-90`).
- Q18 plan edit: `q18.cpp:235-262`. The HAVING threshold is still the parameter `r->qty_bound` (`q18.cpp:241`, `Queries.hpp:234-235`), not a literal.

**Over-tuning.** None in the mechanism. It is a generic "filter group-by output before gathering" API, and Q18 is its only user because Q18 is the only implemented query (Q1, Q3, Q5, Q6, Q9, Q18) with a HAVING clause. The CMake help string names Q18 ("Q18 drops its Select"); that is only a description.

**TPC verdict: OK.** HAVING *is* a filter on the group-by output, so moving the `Select` into the group-by is an exact rewrite for any data and any parameter value. Since the plan is hand-written anyway, writing `.having(...)` is no more query-specific than writing `Select(...)` was.

**Minor:** the Q18 build key changes from the `sel` overload to the dense overload (`q18.cpp:256-262`). That keeps `semiOk` (`scatter_int32_t_col`, `QueryBuilder.cpp:293-294`) and under dispatch leaves `buildKeysSelected` false. That is harmless: 57 keys is below MIN_KEYS either way.

### `VW_GROUP_RUN_HEADS` (committed b8f1b4a)

**Evidence.**
- CMake: `CMakeLists.txt:243-255`.
- Kernel: `keyStepT<..., Runs=true>` (`Operators.cpp:2182-2320`). The comment states the property relied on: "Sorted or clustered keys (Q18: lineitem by l_orderkey) and Q1's 64% repeats both gain" (`:2186-2187`).
- Correctness argument: an entry is reused only on full-key equality with the previous row, so the result is correct for any order (`VW_OPTIONS.md` §2).

**Over-tuning: note.**
- No threshold and no data-dependent branch. It replaces `VW_GROUP_LAST_MATCH`, whose ≥70% switch was a constant fitted between Q1 (64%) and Q18 (75%). The removal fixed a real over-tuning issue.
- The *size* of the gain depends on a data property: dbgen emits lineitem in `l_orderkey` order, so Q18's group-by sees about 75% repeats (`VW_OPPORTUNITY_STUDY.md:139,216`). On a shuffled lineitem the run pass is pure overhead, unmeasured but at most one compare plus a flag per row.

**TPC verdict: OK.** Being faster on clustered input, without depending on it for correctness, is standard: run-length aware aggregation, and Vectorwise and others exploit clustering. TPC-H also permits some physical clustering (Clause 1.5.x (?); exact limits not recalled). The benchmark report should state that the measured gain assumes the dbgen load order.

**Fix:** none needed. Optionally add a shuffled-lineitem run to the ablation to bound the cost of the run pass.

### `VW_PROJ_DENSE` (committed ec81f62, 490eb4b, f484214)

**Evidence.**
- CMake help: "Dense projections over the selected span (TPC-H Q1 prototype)" (`CMakeLists.txt:257-278`).
- The only plan opt-in is Q1: `q1.cpp:386-411` (projections) and `:459-472` (aggregates read through `sel_date`). No other plan references the `proj_dense_*` primitives (grep of `src/`: only `Projection.cpp:148-268` and `Primitives.hpp:1383-1393`).
- Kernels: `denseSpan = inSel[n-1] + 1` (`Projection.cpp:166-168`). All positions up to the last selected one are computed.

**Why it is query-tuned.** The dense path wins only when the selection is dense: the work is `span`, not `n`. Q1's predicate `l_shipdate <= date '1998-12-01' - DELTA` with DELTA in [60, 120] keeps about 95–98% of lineitem. That is a property of the data distribution *and* of the parameter range. At low selectivity (for example Q6's ~2% band) the same transformation would compute up to about 50× more rows than needed. Turning it on in Q1's plan alone is a choice made from knowledge of Q1's selectivity, which a general system would have to estimate or observe.

**Over-tuning: over-tuned (query).**

**TPC verdict: TPC-invalid as is.** It is query-specific plan code, enabled by a query-named build flag, and justified by known data and parameter properties.

**Fix.** Make the decision inside the primitive per vector, for every projection whose operations are total. Use dense when `n * k >= span` for a hardware-derived k, and the selective kernel otherwise. `span` is already computed (`Projection.cpp:166`), so the check costs one compare per vector. Results then have to be position-indexed in both cases, or the consumer has to be told which layout it gets. That is the plan-level part: today Q1's aggregates switch to `aggr_sel_*` under the macro (`q1.cpp:459-472`). Vectorwise's own "full computation" heuristic is the precedent. Once every projection of total operations uses it, Q1 is just one beneficiary.

**Side note (correctness, not compliance).** The scalar tail computes `param1[i] * param2[i]` on int64 for unselected rows (`Projection.cpp:255`). Signed overflow there is UB in C++, while the comment claims these operations "cannot trap" (`:150-152`). It is not a practical risk with TPC-H values, but the claim is stronger than the code: use unsigned arithmetic in the scalar tail.

### `VW_PROJ_DENSE_WIDTH`

**Evidence:** `CMakeLists.txt:262-276`, `Projection.cpp:155-163`: 256-bit to avoid the AVX-512 frequency drop on Cascade Lake.

**Verdict:** **OK / OK.** A hardware fact, chosen per machine at build time like `VW_SIMD_SEL_WIDTH`. It only matters if `VW_PROJ_DENSE` becomes acceptable.

### `VW_Q9_FIELD_ORDER` (older, committed 7c52708)

**Evidence:**
- `CMakeLists.txt:543-571` ("TPC-H Q9: scatter ps_supplycost before n_name");
- `q9.cpp:292-308` (the `addBuildValue` calls swapped under the macro).

**Over-tuning: over-tuned (query).** A build flag named after one query that changes one join of that query.

**TPC verdict: TPC-invalid as is,** as query-specific code. Mitigations: no recommended configuration uses it, and it showed no consistent win (`VW_OPTIONS.md` §3, layout options).

**Fix.** Delete it. If the layout matters, have `HashJoinBuilder` order payload fields by descending alignment for every join (a general rule next to `VW_JOIN_ALIGN_FIELDS`). The previous audit listed it but did not flag it.

### `VW_JOIN_TWOPHASE_MIN_SLOTS` (older)

**Evidence:** `CMakeLists.txt:381-394`; `Operators.cpp:205-213`. The comment cites "TPC-H Q18's 57-order build: 0.9x in run_joinbench on every machine".

**Verdict: note / OK.** Same reasoning as Bloom MIN_KEYS: the cited example is a query, but the threshold sits in a wide gap between TPC-H's tiny and large builds, and its meaning is "directory fits in cache".

**Fix:** derive it from L1d/L2 size.

## Uncertainty and limits

- Spec clause numbers other than 0.2 are marked `(?)`. The substance of the rules is from memory, not checked against the text.
- Selectivities (Q1 ~95–98%, Q6 ~2%) are standard TPC-H figures from memory, not measured here.
- The SF1 bitmap sizes come from the TPC-H key ranges (customer 150K, part 200K, orders key range 6M), not from instrumented runs. `VW_DISPATCH_TRACE=1` (`Operators.cpp:1556-1568`) would confirm the per-join paths.
- No code was built or run for this audit.
